# Transcribe-default page, TranscriptView UX revamp, exact cost tracking, and docx persistence

> **Date**: 2026-09-18
> **Status**: Exploring
> **Scope**: Six related UX/feature changes to the meeting_transcriber Electron app: default page + rename, TranscriptView button revamp (including .txt→.docx export), default text size, a processing modal, exact per-request cost tracking (transcription + summary), and persisting the compte-rendu JSON so its docx can be re-rendered without re-calling the LLM.

---

## Intent

### Problem statement & desired outcomes

The app currently opens on the Record page, uses plain-text export, has no processing modal (transcription is a full page; summary generation is an unguarded inline status line), tracks no API cost anywhere, and discards the paid compte-rendu's structured output the instant its docx is rendered — so recovering from a save failure or wanting a fresh copy later means paying OpenAI again. The user wants:

1. The Upload/Importer page to be the default page on launch, renamed to "Transcrire".
2. Several TranscriptView label/placement revisions (Reset button placement, .txt→.docx export, Copy button label).
3. The default text-size preference raised to the "Très grand" option.
4. A modal spinner shown during transcription and during compte-rendu generation.
5. Exact (not estimated) API cost displayed progressively during processing and in job history.
6. The ability to re-render the compte-rendu docx without re-calling the LLM.

### Success criteria

- **SC1**: UploadView is the default view on app launch. The French sidebar nav label changes from "Importer" to "Transcrire". English label, the page's own heading text, and internal identifiers (`nav_upload` key, `'upload'` view-id) are unchanged.
- **SC2**: The "Réinitialiser la transcription" button moves out of the top header button cluster into its own small, right-aligned toolbar directly above the transcript turns list.
- **SC3**: The transcript export button produces a `.docx` file (replacing `.txt` entirely — not offered as a choice), with button text "Exporter transcript vers .docx". Content mirrors what `.txt` export produces today (speaker name, timestamp, text — respecting the existing `includeTimestamps` preference), rendered as a plain docx document with no additional formatting/styling.
- **SC4**: The "Copier" button is renamed to "Copier transcript" (behavior unchanged).
- **SC5**: The default `fontSize` preference becomes 18 (the "Très grand"/"Extra large" option). The "(défaut)"/"(default)" label suffix moves from the 14/Medium option to the 18/XL option.
- **SC6**: A single shared, reusable modal component (dimmed backdrop, centered card, spinner) is used for both (a) transcription progress — preserving the existing scrolling status log and Cancel button, just restyled as a modal instead of a plain page — and (b) compte-rendu generation — spinner + status message, no cancel button, and its backdrop blocks all TranscriptView interactions underneath (closing the existing gap where Export/Copy/Reset are clickable during a paid, non-cancellable summary request).
- **SC7**: Exact per-request cost is computed and displayed:
  - Transcription: from each provider's own inline usage/duration field (AssemblyAI `audio_duration`, ElevenLabs `audio_duration_secs`, OpenAI `usage.input_tokens`/`output_tokens` incl. `input_token_details.audio_tokens`, Google `usage` token breakdown), multiplied by a per-provider rate.
  - Compte-rendu: from OpenAI Responses API's `usage.input_tokens`/`output_tokens`/`input_tokens_details.cached_tokens`, using the currently-unwired `onUsage` hook in `generate.ts`.
  - Rates live in a new Settings "Pricing" section, pre-filled with today's researched defaults, user-editable (multiple fields per provider where the provider's real pricing has multiple components — see Discovery item 4).
  - Displayed progressively: chunk-by-chunk running total for multi-chunk providers (OpenAI, Google) during processing; appears once, at completion, for single-shot providers (AssemblyAI, ElevenLabs) and for the compte-rendu step (none of these expose a real intermediate signal).
  - Partial cost from completed chunks is retained if a multi-chunk job later fails/cancels. No cost (not `$0`) is shown for a job that fails before any billable unit is ever known.
  - Shown as a single total (transcription + summary combined once both exist) on each HistoryView job card, in USD.
  - Incidental fix folded in: since AssemblyAI/ElevenLabs now surface real audio duration in their completed response, `jobs.duration_s` (currently always `null` in practice — neither RecordView nor UploadView ever supplies it) gets populated from that real value, making HistoryView's existing (currently dead) duration display actually work.
- **SC8**: The compte-rendu's validated `MeetingSummary` JSON and a frozen snapshot of the transcript text it was validated against are persisted (one record per job, latest generation replacing any previous one — mirroring today's in-memory single-slot behavior). Whenever a persisted record exists for a job, TranscriptView shows a "Régénérer le document" action that re-renders and re-saves the docx from the stored data — available at any time later, including after an app restart — without a new LLM call. This upgrades (not duplicates) the existing session-only "Enregistrer à un autre emplacement" retry-save affordance.

### Scope boundaries & non-goals

- No queueing of multiple concurrent transcription jobs (existing one-at-a-time invariant is preserved).
- No history of multiple past compte-rendu generations per job — only the latest is retained (SC8).
- No editing of pricing rates or cost figures for past jobs beyond what SC7's Settings section provides going forward.
- No new external service integration — all five API surfaces used for cost data are already called by the app today; only their response parsing widens.
- No fix for the pre-existing `_activeJobId` stuck-forever bug (runner.ts, `createJob()` can throw before the `try` block, leaving the singleton permanently set) — reported below as a risk, not in scope to fix here.
- No general DB migration framework beyond the minimal `PRAGMA user_version` runner this project needs (see Resolved Decisions, Q1).

### Existing patterns & constraints

- **No DB migration mechanism today**: `src/main/db/index.ts:15-52` embeds one `MIGRATION_001` SQL string, applied via `CREATE TABLE IF NOT EXISTS`/`CREATE INDEX IF NOT EXISTS` inside a transaction (`index.ts:70-77`) on every startup — a no-op on an already-created table. `src/main/db/migrations/001_initial.sql` is a byte-identical copy read only by `tests/unit/db.test.ts` (not at runtime). No `schema_version`/`user_version`/`ALTER TABLE` mechanism exists anywhere in application code. The project's own two-day-old precedent (`plans/260916_TRANSCRIPT_EDIT_TIMESTAMP_FONTSIZE.md`) for adding a column to the live dev database was a **manual** `ALTER TABLE` + timestamped `.bak` copy, run by hand, with both schema-source files updated afterward — no runtime migration code resulted from it.
- **No modal/dialog/spinner UI exists anywhere in `src/renderer`** (confirmed by grep across components/styles — only hits are Catppuccin `--overlay0/1/2` color tokens and Electron's native `dialog.showSaveDialog`). No `position: fixed`/`z-index`/`backdrop` CSS pattern exists to build on — this is new UI, following the existing design-token system (`src/renderer/styles/global.css:9-79`: `--space-*`, `--radius-*`, `--shadow-*`, `.btn`/`.card`/`.form-*` component vocabulary).
- **No provider adapter exposes usage/cost/duration today**: each of `assemblyai.ts`, `elevenlabs.ts`, `openai.ts`, `google.ts` casts its HTTP response to a narrow type naming only the fields currently used (status/utterances, words, segments, steps/annotations respectively) — the billable-unit fields exist in the real APIs (confirmed via live documentation research, not guessed) but are never named in these adapters' types today.
- **`onUsage` hook exists but is unwired in production**: `src/main/summary/generate.ts:33,70` reads `payload.usage` and calls `options.onUsage?.(payload.usage)`, but `src/main/ipc/summary.ts:95` calls `generateSummary(transcript, apiKey, durationMs)` with no 4th argument — the only other caller is `scripts/summary-eval.cjs` (an offline eval harness), so production has always discarded this data.
- **`duration_s` is always `null` in practice**: `StartJobOptions.durationS` (`runner.ts:22-31`) is optional; neither `RecordView.tsx` nor `UploadView.tsx` ever supplies it in their `transcription:start-job` invoke payload (confirmed by grep — zero matches).
- **DB→IPC is a direct passthrough**: `db:get-job`/`db:list-jobs` (`ipc/db.ts:15-21`) return `jobs.getJob`/`jobs.listJobs` (`db/jobs.ts:28-36`) verbatim — a new `cost`/`duration_s` value flows through automatically once in the schema and the `Job` type, but `createJob()`'s INSERT (`jobs.ts:6-9`) and `updateJobStatus()`'s UPDATE (`jobs.ts:12-26`) both hardcode their column lists explicitly — new write paths need explicit new functions or extended signatures, not automatic propagation.
- **IPC registration has no shared middleware**: `src/main/ipc/index.ts:15-28` calls each `register*Handlers()` in sequence with no logging/error wrapper. A new invoke channel needs its shape added to `IpcChannels` (`shared/ipc-types.ts`) — `InvokeChannel` and the preload's typed `ipcApi.invoke` are derived from it automatically — plus an `ipcMain.handle(...)` registration. A new *push* event needs manual addition to the hand-maintained `PushChannel` union in `src/preload/index.ts:6`. Note: `src/renderer/global.d.ts:11-20` declares `window.electronAPI.invoke` with an untyped `channel: string` — channel-name typos are not caught by the type system at any renderer call site today (pre-existing gap, not introduced by this work).
- **Summary persistence today is main-process-memory-only**: `ipc/summary.ts`'s `savedPaths`/`unsaved` Maps (lines 34,37) and `busy` flag (line 31) are lost on a main-process restart; only a renderer reload is recoverable today (via `summary:state`). The validated `MeetingSummary` JSON itself (`ipc/summary.ts:95`) is never stored anywhere and becomes unreachable once the handler returns.
- **Test patterns to follow**: `tests/unit/summary-ipc.test.ts` mocks `electron`/`fs.promises`/db modules/`settings/store`/`render-docx`/`generate` and drives handlers via a captured `mocks.handlers` map — the pattern any new summary-related IPC test should follow. `tests/unit/db.test.ts` execs real SQL from `001_initial.sql` against an in-memory `better-sqlite3` DB — any new column/table must be added to **both** this file and the embedded `MIGRATION_001` string, or the two drift. Per this project's `AGENTS.md`, tests must be run via `npm test` (not raw `vitest`) because of a native-module ABI rebuild step (`pretest`).
- **Decomposition considered and declined**: the six items don't have disjoint file scopes — items 2/4/6 all touch `TranscriptView.tsx`, and items 5/6 both need the same schema-evolution mechanism — so this is written as one combined project file rather than split into per-item child files.

### Risks & mitigations

- **Pre-existing bug, out of scope**: if `createJob()` throws (`runner.ts:51-63`, before the `try` block starts at line 74), `_activeJobId` is never cleared, permanently blocking all future transcription jobs until app restart, and `UploadView.tsx`'s fire-and-forget `transcription:start-job` invoke (no `await`, no `.catch`) would surface this as a silent unhandled rejection with zero user feedback. Reported per the "bugs outside the task are not yours to fix" rule — not to be fixed as part of this work.
- **Universal cost-accuracy caveat**: "exact cost" = billable unit × published standard pay-as-you-go rate. This will not match reality for a provider account on a free tier, subscription credits, or a negotiated rate — no API from any of the four providers can detect which tier an account is on. User confirmed (Q3) all four accounts are standard PAYG.
- **Rate drift is real, not hypothetical**: OpenAI's `gpt-5.6-sol` pricing is explicitly promotional, guaranteed only through 2026-11-21 with an unpublished reversion price; AssemblyAI's pricing page is already ~4 months stale relative to today. Mitigated by making rates Settings-editable (Q3) rather than a fixed constant.
- **ElevenLabs billing rounding is undocumented** — its cost figure may be off by a small, currently unquantifiable rounding amount versus the real invoice. No mitigation available beyond noting this limitation; not blocking.
- **One unverified external contract remains**: whether OpenAI's `gpt-4o-transcribe-diarize` endpoint returns the token-based `usage` shape under that exact field structure (confirmed for the gpt-4o transcription family generally; not shown by name for this specific diarize variant in any fetched documentation). Treated as an execution-contingent Open Item (see below), not assumed.
- **Settings pricing UI is more complex than "one number per provider"**: AssemblyAI/ElevenLabs are duration-based (single rate + diarization add-on); OpenAI and Google are token-based with separate input/output/cached-input rates. The Pricing section needs per-provider field sets that reflect this, not a uniform 4-row table.
- **Persisted summary/transcript-snapshot coupling**: storing a frozen transcript snapshot alongside the JSON (per Q4) deliberately avoids the alternative failure mode — re-validating evidence quotes against a live, possibly-edited transcript at re-render time, which could silently drop citations (`render-docx.ts`'s `evidenceStamp()` returns `null` on no match, not an error).

### Resolved decisions

- Q1: How should the SQLite schema evolve for new `cost` field(s) and persisted summary JSON, given no migration runner exists today? — A: "a+b" (build the minimal migration mechanism now, and use it — rather than a one-off manual `ALTER TABLE` — to perform this change) — Decision: introduce a minimal `PRAGMA user_version`-based migration runner; migration 002 adds the new column(s)/table via this runner, applied automatically to the user's existing `db.sqlite`. Confirmed reading with the user; not corrected.
- Q2: What should "cost" mean for transcription, given no provider returns usage data and duration is never captured today? — A: "exact cost or nothing... can we query credits before/after, or a separate request for cost of a specific request?" — Decision: research whether exact cost is obtainable before deciding on an estimate-based fallback (superseded the original estimate-based recommendation entirely once research answered yes).
- Q2-research: Can any of the five API surfaces report exact per-request cost, inline or via a separate query? — A: (research finding) all five return the exact billable unit inline in the already-called response (AssemblyAI `audio_duration`, ElevenLabs `audio_duration_secs`, OpenAI transcribe `usage` tokens, OpenAI Responses `usage` tokens, Google Gemini `usage` tokens); no provider's separate cost-query API (where one exists) resolves to single-request granularity, and OpenAI's additionally requires an Admin key the app doesn't hold — Decision: compute exact cost locally as inline billable-unit × published rate; no separate cost-query call is needed or viable for any provider.
- Q3: Are all four provider accounts standard pay-as-you-go, and where should the rate table live? — A: "Ok for me" (confirmed PAYG for all four; accepted the recommended approach) — Decision: rates live as Settings-editable fields, pre-filled with today's researched defaults.
- Q4: What should be persisted for docx re-render — JSON only (re-validate against live transcript) or JSON + a transcript snapshot? — A: "Ok" (accepted recommendation) — Decision: persist both the `MeetingSummary` JSON and a frozen transcript-text snapshot from generation time; one record per job, latest replaces previous.
- Q5: Modal design — shared component? Blocking? What happens to the existing transcription page and to Export/Copy/Reset during summary generation? — A: "Ok" (accepted recommendation) — Decision: one shared modal component; transcription keeps its existing status log + Cancel button, restyled as a modal; summary generation gets the same modal with no cancel button, its backdrop blocking all other TranscriptView actions during generation.
- Reset-placement follow-up (AskUserQuestion): where exactly should the Reset button move? — A: "Small toolbar above the turns list (Recommended)" — Decision: SC2 as stated.
- Q6: How far should the "Transcrire" rename reach (FR label, EN label, page heading, internal identifiers)? — A: "Ok" (accepted recommendation) — Decision: French sidebar label only; English label, page heading, and internal identifiers unchanged.
- Q7: Confirm font-size default is 18 (not 20), and where the "(défaut)" label suffix should move — A: "Ok" (accepted recommendation) — Decision: default becomes 18; suffix moves to the 18/XL option label.
- Q8: Cost display granularity and edge-case handling (HistoryView breakdown, progressive-reveal shape, failed-job handling) — A: "Ok" (accepted recommendation) — Decision: single combined total on HistoryView cards in USD; chunk-by-chunk reveal for multi-chunk providers, reveal-at-completion for single-shot providers and the summary step; retain partial cost on mid-job failure; show nothing (not `$0`) when no billable unit was ever learned.
- Q9: Confirm .txt→.docx export fully replaces the old format (respecting `includeTimestamps`), and how the "re-render without paying" action should be surfaced — A: "Ok" (accepted recommendation) — Decision: SC3 and SC8 as stated; the existing session-only retry-save affordance is upgraded to a persistent, always-available "Régénérer le document" action rather than adding a second, separate button.
- Gemini model-ID probe: does the app send the bare `gemini-3.5-transcribe` id or a `-preview` variant (affects which pricing row applies)? — Verified directly (`src/main/providers/google.ts:29`): `const MODEL = 'gemini-3.5-transcribe'` — no preview suffix — matching the primary pricing page found in research. No longer an open question.

### Open items

- **Execution-contingent**: confirm the exact shape of `usage` on a real `gpt-4o-transcribe-diarize` response during implementation (first real call) — expected to be the token-based shape (`input_tokens`/`output_tokens`/`input_token_details.audio_tokens`) per the gpt-4o transcription family generally, but not confirmed by name for this diarize variant in any documentation fetched. If the real shape differs, degrade gracefully (log a warning, show no cost for that job) rather than guessing or crashing.
- **Deterministic, for /qplan to resolve by reading code**: exact new column/table names (`jobs.cost_usd`? a `job_summaries` table?), exact `PRAGMA user_version` bump sequencing, and exact Settings-preference key names for the new pricing fields.

### Recommended approach

Introduce a minimal `PRAGMA user_version` migration runner in `src/main/db/index.ts` (migration 002) that: adds a `cost_usd REAL` column to `jobs` (nullable — absent/unknown until a billable unit is known) and creates a `job_summaries` table (`job_id TEXT PRIMARY KEY REFERENCES jobs(id) ON DELETE CASCADE`, `summary_json TEXT NOT NULL`, `transcript_snapshot TEXT NOT NULL`, `created_at INTEGER NOT NULL`) — mirrored into `001_initial.sql`-equivalent test fixtures per the existing dual-copy pattern. Widen each provider adapter's response type to also capture its billable-unit field (`audio_duration`, `audio_duration_secs`, `usage`), and thread real per-provider/per-chunk cost through `runner.ts` into `jobs.cost_usd` (progressively for chunked providers). Wire `generate.ts`'s existing `onUsage` hook in `ipc/summary.ts`'s production call site to capture the summary's real cost. Add a Settings "Pricing" section (per-provider rate fields, defaulted from today's researched values) as new `PreferenceKey`s. Build one shared Modal component and use it in both `JobProgressView` (restyled, same content) and `TranscriptView` (new, during `summarizing`). Persist the `MeetingSummary` JSON + transcript snapshot in `job_summaries` at the point `ipc/summary.ts:95`'s `renderSummaryDocx` call currently discards it, and add a `summary:rerender`-style IPC channel that reads the stored record and re-invokes `renderSummaryDocx` without touching `generateSummary`. Apply the remaining label/placement/default-value changes (SC1-SC5) as straightforward, low-risk edits to `App.tsx`, `Sidebar.tsx`, `i18n.ts`, `TranscriptView.tsx`, `SettingsView.tsx`, and `settings/store.ts`.

### QA environment

- Unit tests: `npm test` from repo root (never raw `vitest` — `pretest` rebuilds `better-sqlite3` for the Node ABI first). The suite is 16 files; a lower count silently indicates a skipped/broken suite, per this project's own `AGENTS.md`.
- Manual E2E: `npm run dev` launches the Electron app (rebuilds native modules for the Electron ABI automatically via its own script). Verifying cost tracking end-to-end requires real, configured API keys for at least one transcription provider and for OpenAI (compte-rendu), and will incur small real charges — consistent with this project's existing testing-cost precedent (~$5-10/provider, documented in the founding plan).
- DB migration testing: run the new migration runner against a **copy** of the real `userData/db.sqlite` (with a backup taken first, per this project's own established precedent) to confirm existing jobs/transcripts survive the schema change untouched.
- No fixture in the repo currently captures a real provider HTTP response body (only transcript-level golden data exists under `tests/fixtures/municipal-summary/`) — new unit tests for the widened provider adapters will need hand-built synthetic response fixtures including the new usage/duration fields, following the existing per-provider mocking pattern in `tests/unit/providers/*.test.ts`.
